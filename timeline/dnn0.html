01 System architecture — what runs where on your i5
The core problem: GNN inference can't block the game loop
Your i5 8th gen has 4 cores. The solution is to split work across them cleanly. Pygame's game loop runs on the main thread. The GNN inference runs on a separate background thread. They communicate via a thread-safe queue — no sockets, no HTTP, no serialization overhead. Pure in-process Python threading.

Why this doesn't melt your laptop
The GNN only gets called every 6 frames (10 times/second), not every frame. Between calls, the AI jet uses the last cached prediction to continue its move. This is called "inference on a sub-tick schedule." Result: GNN thread runs at ~10Hz, game renders at 60fps, your CPU sees ~15% load total. No melting.

PyTorch on CPU for a 3-layer MLP with ~5 nodes takes 1–3ms per forward pass. 10 calls/sec = 10–30ms of CPU per second. Completely fine.

02 GNN integration — how the AI jet actually makes decisions
The decision loop (Model Predictive Control, simplified)
Every 6 frames, the GNN thread does this:

1. Sample 5 candidate moves for the jet: [+30°, +15°, 0°, -15°, -30°] heading deltas
2. For each candidate, project positions forward 10 frames using simple velocity math (no GNN yet, just kinematics)
3. Build a scene graph for each projected state: jet + all active missiles + flare particles as nodes
4. Run the GNN on all 5 scene graphs in a single batched forward pass
5. Pick the move where the GNN's max edge collision probability is lowest
6. Also check: if survival probability > 0.8 AND distance to target < threshold → switch to "attack mode"
7. Push the chosen move back to the main thread via the queue

Total: 5 forward passes per decision. At ~2ms each = ~10ms. Well within budget.
Scene graph structure (maps directly to your existing notebook)
Nodes: jet (1), active missiles (up to 8), flare particles (up to 12 per flare burst, max 2 bursts active)
Node features: [pos_x, pos_y, vel_x, vel_y, obj_type, obj_size] — 6 features
Edges: fully connected between all nodes
Edge features: [rel_pos_x, rel_pos_y, rel_vel_x, rel_vel_y] — 4 features
Edge labels (training): binary — did these two objects collide in the next N frames?

Your existing notebook uses node_dim=9, edge_dim=6. You'll retrain with these new dimensions. The architecture stays identical.
Why your existing GNN data is broken — and the 10-line fix
Your current data generator assigns collision labels randomly. The model learns nothing real. Before running the game, replace the collision detection with actual physics:

dist = sqrt((pos_i[0]-pos_j[0])² + (pos_i[1]-pos_j[1])²)
is_collision = 1 if dist < (radius_i + radius_j) else 0

That's it. Two lines. Now the GNN learns real physics instead of noise.
03 Game physics & logic — the exact math
Fluid movement (all objects)
Every object has (x, y, vx, vy, heading).

Per frame update:
heading += turn_rate * dt
thrust_x = cos(heading) * speed
thrust_y = sin(heading) * speed
vx = vx * drag + thrust_x * dt
vy = vy * drag + thrust_y * dt
x += vx * dt
y += vy * dt

Jet drag: 0.92 (drifty, feels kinetic)
Missile drag: 0.98 (tight, fast)
Flare drag: 0.85 (spreads wide and slows)
Missile → target homing
Standard proportional navigation. Each frame:

dx = target.x - missile.x
dy = target.y - missile.y
desired = atan2(dy, dx)
diff = normalize_angle(desired - missile.heading)
missile.heading += clamp(diff, -turn_rate, turn_rate)

Homing missiles track the jet.
Dumb missiles fly straight — player must aim.
Mix both types to create different challenge layers.
Flare cluster mechanic
When the AI fires a flare burst, spawn N=8 particles in a fan pattern:

for i in range(N):
  angle = jet.heading + 90° + (i - N/2) * spread/N
  angle += random(-jitter, +jitter)
  speed = base_speed + random(-v, +v)

spread = 60°, jitter = 8°

The gaps are real and random. Missiles that thread between particles pass through. Missiles that hit a particle trigger a collision. The GNN models each particle as its own node.
Collision detection
Pure circle-circle, checked every frame:

dist = hypot(a.x-b.x, a.y-b.y)
if dist < a.r + b.r: collide(a, b)

Jet radius: 12px
Missile radius: 4px
Flare particle radius: 6px

Missile-missile collision: both explode, particle effects.
Missile-flare collision: flare particle dies, missile dies.
Missile-jet collision: jet dies, user wins.

Broad phase: skip pairs farther than 80px to save CPU.
Win / loss conditions
User wins: missile hits jet before timer = 0.
AI wins: timer reaches 0 AND jet is alive → jet fires payload at corner target. The payload is a large slow projectile with a 3-second travel time and a big explosion radius. Dramatic finish.
Timer: 15 seconds, displayed as a glowing ring around the map edge that drains.
04 Visual aesthetic — neon radar without frying your GPU
The core trick: fake glow with Pygame alpha surfaces
Real glow requires a GPU blur pass. Instead, draw each glowing object 3 times:

1. Outer halo: large circle, color at 30 alpha → feels like diffuse glow
2. Mid ring: medium circle, color at 80 alpha
3. Core: small circle, color at 255 alpha (fully bright)

This is 3 alpha-blended circles per object. Costs almost nothing on CPU. Looks like a real glow. This is how old-school retro games did it.
Color palette
Background: #050A14 (near-black blue)
Grid lines: #0A1F3A (dark teal)
Jet: #00FFC8 (cyan)
Player missiles: #FF4444 (red)
Flares: #FFB020 (amber)
Target: #FF00AA (magenta)
Timer ring: fades from cyan → red
Background radar grid
Draw once to a static surface on init:

— Concentric circles at r = 80, 160, 240, 320
— 8 radial lines at 45° intervals
— All at alpha 40–60
— Rotating sweep line: 1 bright line rotating at 1 rev/3 seconds, leaves a fading trail using decreasing alpha buffer

This is the entire background. Render it once, blit every frame.
Particle trails
Each missile stores last 12 positions in a deque.

Draw trail segments from oldest to newest, with alpha decreasing from 20 → 180.

Width tapers from 1px → 3px.

Flare particles get shorter trails (6 positions) in amber.

The jet gets a longer trail (20 positions) in cyan with slight width variation — makes it look like it's burning thrust.
Explosion effect (pure CPU, no shader)
On collision: spawn 16–24 "shrapnel" particles with random velocities in a full 360° spread. Each particle:
— Starts bright (alpha 255), fades to 0 over 20 frames
— Has a short 4-position trail
— Has a random speed between 2–8 px/frame

Additional: one large expanding circle that starts at radius 8, expands to 40 over 12 frames, alpha fades from 200 → 0. This gives the "shockwave" feel.

Total cost: ~24 extra particles for ~20 frames each. Nothing on an i5.

What the headless simulator does
Pure Python physics — no graphics, runs at 10,000x real-time speed. A "dumb jet" moves randomly. Random missiles fire at it. Flares deploy randomly. Every 2 frames, log all object positions, velocities, types, and which pairs collide within the next 8 frames. Save as JSON.

Generate 5,000 rounds × 15 seconds × 30Hz = ~2.25M frames. This trains in ~15 minutes on T4. You only need ~500k frames minimum — be conservative to stay on schedule.

07 The DNN story — what to tell your professor
The game isn't the project. The GNN is. The game is just the most engaging possible demo environment. Your talking points:

1. Graph Neural Network for multi-agent physics prediction — your Interaction Network models each object as a node, uses message passing to propagate physical interactions, and predicts future collision probabilities.

2. Dual use of the same model — the GNN is used for evasion (choose the move with lowest collision probability) AND flare deployment timing (deploy when a missile's predicted trajectory intersects the jet's position).

3. Synthetic data generation for a custom physical domain — you designed a physics simulator, generated training data, and trained the model to generalize to an unseen game environment.

4. Real-time inference under latency constraints — the model runs at 10Hz in a separate thread, demonstrating inference optimization for resource-constrained environments.
